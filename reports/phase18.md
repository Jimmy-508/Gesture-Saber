# Phase 1.8 — Grip Control

基準：`cfdc54ee3907116363207604eca35b299fd5b182`。正式網址：https://jimmy-508.github.io/Gesture-Saber/ 。本次只更換雙頭方向策略、變形流程與音訊排程／生命週期；單頭操作、主控身分政策、模型、門檻、攝影機解析度與推論頻率均保留。

## 握柄方向的估計

`src/grip-pose.ts` 是方向估計策略，不是另一套手部控制核心。它沒有位置、身分、速度預測、MotionFilter 或渲染器。雙拳靠攏指令沿用 Phase 1.7，第二隻手仍只參與指令；只有原主控手的觀測送入 GripPose。

握拳的手指彎曲平面近似環繞圓柱握柄的橫截面：分別以每指 MCP→PIP 與 PIP→DIP 的三維叉積估計穿出方向，至少兩指的法向一致才採用。用拇指根部相對小指掌部的方向決定軸線正端。此方向不是腕→中指 MCP，也不是直接採用 MCP5→17 的四指排列向量。測試骨架刻意讓握柄軸與 MCP 排列不同，防止捷徑實作通過。

在進入雙頭時把這個軸線存為掌部局部座標；之後以手腕與掌部 MCP 的三維座標搬移。張開手指不會重新學習成另一個方向，也不必繼續握拳。世界座標優先，與影像座標明顯矛盾時走影像備援；方向資料不足時保留合理旋轉，位置仍由原控制器更新。左右手正端由解剖資訊決定，roll 配合原掌部法向，鏡像骨架 quaternion 對稱；中立握持從單頭方向轉約 ±90°，沒有單側額外半圈。單次大幅異常反轉需確認，正常連續轉腕沒有額外角速追趕限制。

`src/control-core.ts` 只新增可選的方向目標，仍共用唯一 ControlHand 與既有單層防抖。單頭未傳入 Grip 目標，125 項測試中的固定 Phase 1.7 比較逐幀確認兩手位置及旋轉輸出不變。雙頭不會再次通過舊 PalmPose／旋轉限速。舊核心回退保留原位置路徑，雙頭旋轉採 Grip，避免疊加舊旋轉追趕；沒有第二把武器或第二組位置。

## 正式變形流程

`src/weapon-morph.ts`：

1. RETRACT 120 ms：原光刃（或原雙刃）收回，金屬握柄及主控位置持續存在。
2. ALIGN 60 ms：兩端光刃皆為零；顏色切換，握柄完成轉向。
3. EXTEND 160 ms：依新模式伸出兩端金色光刃，或原手色的單刃。

同一父節點、同一主控位置始終保留。只有最初 180 ms 使用有界的旋轉銜接；之後直通既有單層控制輸出，沒有持續追趕動畫。中途再切換會從當前伸展量及旋轉接續。關閉雙頭也先收雙刃、保留握柄、回到單頭方向再伸出原色主刃。方向失準不會收劍，真正遺失主控仍沿用原 260／420 ms 收起及隱藏保護。

原 1.5 倍握柄、按鈕與環紋、光刃長度／半徑／尖端、Shader 字串及光帶生成器保持。自動變形期間不把轉向當作真實揮劍速度產生破風聲；舊光帶自然衰減。光源數量與畫質策略不增加。

## 音效：保留聲音，移除無意義的工作

原 `createVoice()` 圖、噪聲生成、振盪器波形、音高／諧波關係、濾波 Q、`soundForSpeed()`、開收劍頻率及音量包絡不變。Phase 1.1 原始事件圖回歸仍精確通過。沒有下載音效素材、重新製作音色、OfflineAudioContext 生產素材或重建預載架構。

找到的程式問題：Phase 1.7 相同目標在首秒仍反覆 cancel／setTarget；速度微小變化又會重設等待時間。此外 App 每次停止會 dispose 音訊圖，下一次啟動再次配置八個來源與兩份 Noise Buffer。

修改如下：

- 相同目標立即略過；微小連續變化使用絕對／相對 deadband，仍提交原始計算值，不把音高量化成新的音階。振盪器約 0.1 Hz 或 0.1%，濾波約 1 Hz 或 0.2%，Gain 約 0.00015 或 0.3%；兩個音高與兩個濾波器成對維持原關係。
- 伸縮造成的 Gain 變化不使用 deadband，精確零一定提交，原時間常數與開收劍包絡保留。沒有新增音訊更新率上限或固定等待時間。
- 變形不再額外 pulse 疊聲，而是由 RETRACT／EXTEND 各觸發一次原始收劍／開劍邊緣，同一聲道、同一待機聲。
- 停止攝影機後先讓原 12 ms 靜音包絡衰減，50 ms 後 suspend；切頁直接 suspend。這是一份每頁最多一組的有界快取，重新點擊攝影機以使用者手勢 resume，沒有重新建立聲音節點或噪聲緩衝。暫停後把閒置 Gain 歸零，避免重啟殘聲。
- 快速重啟會取消尚未執行的 suspend，epoch 阻止過期非同步操作影響新狀態。靜音時不進行每幀參數排程。pagehide／卸載停止所有來源、斷線並關閉 context。

## 同場景音效比較

以下為最終 `phase18-core.json`：桌面 Chromium、約 1024×768／1×，同一個正式 Three.js 場景與固定 24 Hz 合成輸入；每案 60 個暖機、120 個量測邏輯影格，順序靜音→舊音訊→新音訊→靜音。聲音測試音量 3%，靜音案的 context 均 suspend。只換音訊實作，GPU／姿態輸入相同。每案的觀測總數均為 72，沒有增加模型推論。

| 同一個正式場景 | Phase 1.7 音訊 | Phase 1.8 音訊 |
| --- | ---: | ---: |
| AudioParam API 呼叫／120 次繪圖 | 1440 | 580 |
| 音訊更新 CPU 平均／P95／峰值 ms | 0.045 / 0.100 / 0.200 | 0.019 / 0.100 / 0.200 |
| 繪圖迴圈間隔 平均／P95／峰值 ms | 19.522 / 31.300 / 32.100 | 19.425 / 30.400 / 32.300 |
| 場景 CPU 平均／P95／峰值 ms | 0.512 / 1.000 / 1.200 | 0.454 / 0.800 / 1.100 |

AudioParam 呼叫減少約 59.7%。音訊更新平均成本較低，但單次計時解析度約 0.1 ms，P95 與峰值沒有明顯改善；不能把微小平均差距直接解讀成實機效果。

靜音前／後的繪圖間隔 P95 約 31.2／30.8 ms，峰值 32.0／42.8 ms；與有聲案相近。此環境的計時器有節流與量化，表中是牆鐘繪圖迴圈間隔，不是螢幕 FPS。沒有證據支持音效是平板卡頓主因，也不宣稱這次音效精簡改善 FPS。原本來源圖的冷啟動準備耗時也受 JIT／量測順序影響，不當作音色或性能優劣結論。可確定的是正式 App 兩次開啟攝影機重用同一引擎與兩份 Noise Buffer。

功能檢查另使用正式 React／receive／WebGL 與獨立測試繪圖時鐘；它可能與瀏覽器 RAF 共存，因此功能記錄中的影格頻率不可當作真實 FPS。上表獨立場景關閉自動 RAF，只有一個測試繪圖迴圈。

## 待平板實機確認

需要使用者確認左右手真實握柄穿出方向與 roll、握拳切換到自然張掌後的連續性、遮擋及深度估計不穩時的姿態、快速轉腕與停止、Safari 的音效啟用／靜音／重啟與聽感、實際幀時間及熱降頻。握持軸是關鍵點幾何估計，並非直接量得真實物理握柄；模型若沒有足夠曲指平面或掌部方向，會保留合理旋轉，不憑空推測軸線。沒有真實平板、相機端到端延遲或真實物理握持驗收結論。
